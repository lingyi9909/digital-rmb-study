# 第二周 Day 6｜一笔数字人民币支付如何完成？支付、清算、结算和风控

## 目标
沿着用户点击“支付”到商户资金可用的过程，区分用户指令、运营机构账务、跨机构消息、最终结算以及失败恢复机制。

## 一、先建立三个不同动词
- **支付**：付款方发起并完成向收款方转移价值以清偿债务的过程。
- **清算**：各方确定应收应付、核对和处理交易信息；可能涉及净额计算。
- **结算**：按照清算或支付指令转移结算资产，完成相应资金债务的最终清偿。
不同系统里“支付完成”“入账成功”“最终结算”并非永远同一时间点，需要遵守具体系统规则。

## 二、场景：银行A数币钱包向银行B商户支付100元
~~~mermaid
sequenceDiagram
    participant U as 用户
    participant A as A行数字人民币钱包
    participant P as DCEPS/跨机构基础设施
    participant B as B行数字人民币钱包
    participant M as 商户
    U->>A: 确认支付100元并认证
    A->>A: 检查余额、限额、反欺诈
    A->>P: 发起符合规则的跨机构交易
    P->>B: 交易转接/校验等
    B->>B: 核验商户收款钱包
    B-->>P: 处理结果
    P-->>A: 结果反馈
    A-->>U: 付款结果
    B-->>M: 收款结果
    Note over A,B: 跨机构资金清结算依系统规则完成
~~~
**这是教学抽象图**，不是官方公布的逐接口时序，也不能据此认定每一笔交易实时逐笔通过央行总账结算。

## 三、把“账”分成四层看
1. 客户体验层：支付订单ID、商户订单号、交易进度与凭证。
2. 钱包运营层：借贷记账、余额、限额、利息、风险与退款。
3. 跨机构交换层：格式规范、幂等、重复报文、防重放、状态确认。
4. 结算与对账层：机构间债务清偿、日终/实时核对、异常处理。

## 四、系统工程重点：幂等比“重试直到成功”更重要
假设用户点击付款后手机超时：
- 第一笔请求可能已经在服务端成功；
- 用户再次点击会触发新的请求；
- 若系统没有幂等键、唯一交易号和可靠状态机，可能重复扣款。

推荐学习状态机：
~~~mermaid
stateDiagram-v2
    [*] --> Created
    Created --> Validating
    Validating --> Failed: 校验不通过
    Validating --> Processing
    Processing --> Succeeded: 确认成功
    Processing --> Pending: 结果未明
    Pending --> Succeeded: 查询核实成功
    Pending --> Failed: 确认未生效
    Succeeded --> Refunding: 合法退款申请
    Refunding --> Refunded: 退款完成
~~~
注意：成功后的“退款”通常是独立反向资金操作，不是直接删除原交易记录。对于结果未明的交易，盲目重试可能造成重复支付，应先查证交易状态。

## 五、风控体系可以用“六道关口”理解
|环节|典型风险|思路|
|---|---|---|
|钱包开户|虚假身份、冒名注册|分层身份核验、设备风险|
|登录授权|账号接管、社工欺诈|多因素认证、异常登录预警|
|付款发起|欺诈收款、交易篡改|商户校验、限额、风险评分|
|交易执行|重复扣款、超时不一致|唯一交易号、幂等、原子账务设计|
|资金流转|洗钱、异常拆分、团伙交易|依法依规识别异常模式并报告|
|售后对账|退款失败、长短款|对账闭环、差错处理、人工复核|

金融安全还包括内部人员权限管理、密钥轮换、审计日志、防止日志泄露用户敏感数据以及灾备。

## 六、双离线意味着什么？
离线方案必须考虑：脱机余额或凭证、抗双花机制、离线额度、防重放、设备物理安全、回联后处理和争议责任。某些已适配设备可以在特定条件下无网或无电支付，但不应泛化为“所有数字人民币钱包无网无电都能用”。

## 七、2026央行基础设施如何服务这套流程？
2026年10月公开材料介绍央行端DCEPS提供跨机构支付结算、流动性管理、智能合约生态、发行与钱包管理等服务，还涉及与跨境结算平台CBETS的协同。**产品设计必须区分公开能力与未公开接口实现**，不能凭教材推测真实内部API。

## 八、工程实践练习
设计一个简单的支付订单表，至少包括：
~~~text
payment_order(
  payment_id,
  payer_wallet_ref,
  payee_wallet_ref,
  amount,
  currency,
  idempotency_key,
  status,
  created_at,
  updated_at
)
~~~
这是教学演示，真实系统还需要审计、风险、凭证、对账和隐私保护等字段/能力。
回答三个问题：
1. 如果超时但服务端已扣款，再次请求如何避免重复扣？
2. 收款方已入账、付款方显示处理中如何处置？
3. 用户需要退款时，为什么不能直接把原流水删除？
